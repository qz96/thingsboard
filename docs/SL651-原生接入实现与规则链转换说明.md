# SL651 原生接入：实现逻辑、新增模块、部署模式与规则链转换

> 基线：ThingsBoard **4.2.1.1** fork，新增 SL651 原生 transport（方案 A：平级接入）。
> 本文从"为什么这样实现 → 改了哪些模块 → 不同部署模式怎么改 → 如何用规则链把 SL651 转成兼容既有技术线"四个维度说明，供团队直接落地与交接。
> 配套脚本：[`sl651-to-hj212-transform.js`](./sl651-to-hj212-transform.js)。

---

## 1. 概述与目标

把 SL651（水文监测数据传输规约）遥测站当作 **ThingsBoard 的一等公民设备**接入，而非继续走"独立网关翻译成 JSON 再丢 MQTT"的旁路方案。

- **目标 A（接入）**：SL651 通过 TCP :8501 直连 TB，完成认证、会话、遥测/属性上行、RPC 下行，与 MQTT/HTTP/COAP 平级复用 TB 传输 SPI。
- **目标 B（兼容既有技术线）**：遥测落库键使用**稳定、无语言依赖的要素编码**，再通过**规则链 Transform 脚本**把要素编码翻译成旧网关（sl-gateway）一直使用的 **HJ212 污染因子编码**，从而让下游的看板、告警、对接系统零改动直接复用。

---

## 2. 总体架构与数据流

```
 SL651 遥测站（TCP 客户端）
        │  7E 7E ... 报文帧（水位/雨量/流量/水泵等观测要素）
        ▼
┌──────────────────────────────────────────────┐
│ SL651 Transport（TCP Server :8501）         │  <- 新增 common/transport/sl651
│  Sl651FrameDecoder   帧同步/粘包半包         │
│  Sl651SessionHandler 认证+会话+上行+下行      │
│  Sl651TransportService @Component 拉起        │
└──────────────────────────────────────────────┘
        │ token = 前缀+站码（ACCESS_TOKEN）
        │ PostTelemetryMsg / PostAttributeMsg / RPC
        ▼
│      transport-api（TransportService SPI）   │  <- 复用 TB 既有
        │  in-memory（单体）或 Kafka（MSA）
        ▼
  TB 核心 / 规则引擎 / 时序存储
        设备在线态、遥测/属性入库、规则链、RPC 路由
```

关键点：SL651 传输**只接入 TB 的 transport 层**，不侵入 actor、存储、规则引擎内核。

## 3. SL651 集成的具体实现逻辑

分四层：协议解析层、传输/链路层、数据模型层、前端层。

### 3.1 协议解析层（`common/transport/sl651` 的纯解析类）

> 方向：把不可读的二进制帧解析为领域对象，不关心 TB 细节，便于单测与复用。

| 类 | 职责 |
|---|---|
| `ControlChar` | 定界符/控制字符常量（`0x7E` 起始结束、`STX/ETX` 等） |
| `CRC16` | 帧校验（CRC16-IBM，含转义处理） |
| `FunctionCode` | 功能码常量（如 `0x01` 链路维持、`0x0F` 遥测、`0x27` 实时遥测、`0x35` 人工置数报等） |
| `StationType` | 遥测站类型 |
| `ElementIdentifier` | 要素标识符（完整 2 字节：引导符 `<8` + 属性字 `>8`） |
| `DataElement` | 单要素：标识符、测点、BCD 解析出的值 + **完整标识符** `getFullIdentifier()` |
| `SL651Parser` | 把帧字节解析为结构化 `SL651Frame`，解密 BCD 值（非法返回 `NaN`） |
| `SL651Frame` | 帧模型：功能码、中心站/遥测站地址、密码、数据要素、**原始帧字节 `rawFrame`** |

### 3.2 传输/链路层（Netty 管线 + 会话处理器）

**链路初始化（`Sl651TransportServerInitializer` + `Sl651FrameDecoder`）**
- 报文进入 `Sl651FrameDecoder` 做**帧同步**：按 `7E` 起始符 + 长度字段 + `7E` 结束符定位完整帧边界，**容忍粘包/半包**，超长帧直接丢弃并计入异常。
- 之后交给 `Sl651SessionHandler`（继承 `SimpleChannelInboundHandler<SL651Frame>` 并实现 `SessionMsgListener`）。

**设备认证（`validateAndConnect`）**
- 以 `token = transport.sl651.token_prefix（默认 sl651） + 遥测站地址（BCD 10 位站码）` 作为设备的 **ACCESS_TOKEN** 调用
  `transportService.process(SL651, ValidateDeviceTokenRequestMsg, cb)` 完成凭据校验。
- **为什么加前缀**：不同协议（如 SL427）站址在全局凭据命名空间里可能撞码，前缀 `sl651` 与网关侧约定一致，实现协议隔离。
- 认证期间到达的帧先入 `pendingFrames` 队列，注册成功后再批量上行。

**会话建立（`openSession`）**
- 校验通过 → `SessionInfoCreator.create` 构建 SessionInfo → 上报 `SESSION_EVENT_MSG_OPEN` → `registerAsyncSession(info, this)`，设备进入"活跃"态。

**上行分流（`processFrame`）**——核心路由
```java
storeRawFrame(frame);                        // ① 原始帧存档（见下）
kvList = buildKvList(frame);                  // ② 要素 → 遥测键值
if (profileConfig.isStatusReportAsAttribute() && isStatusReport(frame))
    → PostAttributeMsg（走设备属性）
else
    → PostTelemetryMsg（最新遥测）
```
- `isStatusReport` 现**仅按功能码 `0x35`（人工置数报）判定**，避免"帧内含一个 0x45 状态要素就把整帧误判为状态报、导致正常遥测整体被路由到属性"。

**下行 RPC（`onToDeviceRpcRequest` + `Sl651RpcMethod` + `Sl651CommandEncoder`）**
- `method → 功能码` 映射（查实时/查状态/对时/改密/读配置等，见 `Sl651RpcMethod`）。
- `Sl651CommandEncoder.build(最近上行帧头, 功能码, 参数)` 组下行命令帧 → `writeAndFlush` → 上报 `RpcStatus.DELIVERED` → 登记待回复 RPC。
- 上行帧功能码落入某命令的**应答功能码集**时，用终端帧数据构造 JSON 负载回执 `ToDeviceRpcResponseMsg(requestId, payload)`。

### 3.3 数据模型层（`common/data`）

- `DeviceTransportType` 新增枚举 `SL651`，并在 `@JsonSubTypes` 注册两个配置类：
  - `Sl651DeviceProfileTransportConfiguration`（Profile 级）：`telemetryKeyPrefix` / `statusReportAsAttribute` / `reportTypes`。
  - `Sl651DeviceTransportConfiguration`（设备级）：`stationAddress` / `key`。
- 认证：设备凭据 = **ACCESS_TOKEN，token = 前缀+站址**。

### 3.4 前端（`ui-ngx`）

- `DeviceTransportType.SL651` + 对应接口/类型 + 设备 Profile 传输类型下拉分支。
- `Sl651DeviceProfileTransportConfigurationComponent`（含空安全：对缺失 `configuration` 的 profile 做兜底）。
- `home-components.module` 注册 + `locale.*` 文案。

### 3.5 关键设计决策（为什么这么落）

1. **遥测键 = 要素编码（有用），而非中文要素名**：
   - `buildKvList` 中 `key = applyKeyPrefix(String.format("%04X", element.getFullIdentifier()))`，即完整 2 字节数据标识符（如 `4612`/`4711`/`4818`…）。
   - **原因**：要素编码跨语言、跨版本稳定；中文/命名映射下沉到**规则链 JS**，可随时改映射而不用重编 Java。这是"兼容既有技术线"的前提。
2. **键前缀可配但默认不加**：`applyKeyPrefix` 仅在前缀非空、非 blank、且不等于 `sl651` 时才加 `前缀_`，默认裸编码键，减少冗余。
3. **原始帧存档**：`storeRawFrame` 把整帧十六进制留为设备 client 属性 `rawFrame`（覆盖写仅保留最新一帧）。**原因**：便于协议排障、离线重放、审计，且不影响正式遥测入库。
4. **token 前缀隔离**：`sl651` 前缀避免跨协议站码撞码。
5. **状态/遥测分流下沉到实现而非把 `&config` 全部当属性**：语义清晰，下游看板按需取最新遥测。

## 5. 不同部署模式下的改动及其原因

SL651 同一份代码支持两种跑法：**单体内嵌** 与 **独立微服务**。二者对核心代码**无改动**，只有"启动方式 + 队列类型 + 部署工件"有差异。

### 5.1 模式 A：单体内嵌（单节点 / in-memory，`application`）

- **改动**：`application` 的 `thingsboard.yml` 中 `transport.sl651.enabled`（默认 `true`）；`common/transport/sl651` 作为依赖打进 monolith，`Sl651TransportService` 被组件扫描自动拉起，**同一 JVM** 内起 TCP :8501。
- **原因**：开发/单机试点最简，无需 Kafka；传输与核心 via in-memory 同进程通信，链路最短、易调试。
- **队列**：`queue.type=in-memory`。

### 5.2 模式 B：独立微服务（MSA / Kafka）

- **改动**：单独部署 `transport/sl651`（`tb-sl651-transport`），端口 8501，与 `tb-core` 平行；配置 `tb-sl651-transport.yml`。
- **原因**：生产多节点/集群要水平扩展与隔离；SL651 传输与核心跨进程，必须用 Kafka。
- **队列**：`TB_QUEUE_TYPE=kafka`，走 `tb_transport.api.*`。
- **编排**：`docker-compose.yml` 已就位 `tb-sl651-transport1/2`（依赖 zookeeper + tb-core）。

### 5.3 对比与改动原因速查

| 维度 | 单体内嵌（in-memory） | 独立微服务（Kafka/MSA） |
|---|---|---|
| 进程 | 内嵌于 monolith（单 JVM） | 独立 JVM（`tb-sl651-transport`） |
| 端口 | 8501 | 8501 |
| 消息队列 | in-memory | Kafka（**必须**） |
| 启动方式 | 随应用启动 | 单独部署 / `docker compose` |
| 配置入口 | `application#thingsboard.yml` | `tb-sl651-transport.yml` + env |
| 适用场景 | 开发 / 单机 | 生产多节点 / 集群 |
| 本机验证 | ✅ 已端到端验证 | 待 Kafka 验证 |

> **注意**：两种模式**都默认监听 8501**。同一主机若同时跑"内嵌单体"和"`tb-sl651-transport` 微服务"会**端口冲突**，同一环境二选一，或改 `transport.sl651.bind_port`。

## 6. 规则链：把 SL651 转成兼容既有技术线

### 6.1 目标

SL651 落库键是要素编码（如 `4612`），但旧 sl-gateway 一直用 **HJ212 污染因子编码**（如 `W21003` pH）。我们要在不改 Java、不动下游的前提下，让旧看板/对接系统直接读到它认识的键。

做法：**规则链 Filter + Transform**，在入库（Save Timeseries）**之前**把要素编码键翻译成 HJ212 污染因子键。

### 6.2 规则链节点编排

```
 入口（Root Rule Chain）
   │
   ▼
  Message Type Switch
   ├─ POST_TELEMETRY_REQUEST  → SL651→HJ212 子链（或直接内联下列节点）
   └─ 其它                     → 原逻辑
             │
             ▼
      Transform Script 节点      ← 粘贴脚本：要素编码 → HJ212 污染因子
             │
             ▼
      Save Timeseries            ← 以 HJ212 因子编码落库（兼容旧网关）
```

要点：
1. 建议放进独立子规则链，`Message Type Switch` 按 `msgType==POST_TELEMETRY_REQUEST` 路由，避免脚本污染属性/RPC 消息。
2. 脚本用 `msgType` + `metadata` 即可，Slot 保持 `Success`/`Failure` 语义。
3. 若需同时保留原始编码键，脚本里放开 `result.raw = msg` 的注释。

### 6.3 Transform 脚本（要素编码 → HJ212 污染因子）

完整脚本见 [`docs/sl651-to-hj212-transform.js`](./sl651-to-hj212-transform.js)，核心：

```javascript
var FACTOR_MAP = {
  '4612': { code: 'W21003', name: 'pH' },
  '4711': { code: 'W21001', name: '溶解氧' },
  '4818': { code: 'W21021', name: '氨氮' },
  '4910': { code: 'W21011', name: '浊度' },
  '4A11': { code: 'W21005', name: '电导率' },
  '4C1A': { code: 'W21016', name: '总磷' },
  '4D1B': { code: 'W21017', name: '总氮' },
  '4E1A': { code: 'W21019', name: '高锰酸盐指数' },
  '4520': { code: 'D001', name: '遥测站状态及报警信息' },
  '381A': { code: 'D002', name: '电源电压' }
};

var result = {};
var keys = Object.keys(msg);
for (var i = 0; i < keys.length; i++) {
  var f = FACTOR_MAP[keys[i]];
  if (f) result[f.code] = msg[keys[i]];
}
// result.raw = msg;   // 可选：保留原始编码键
return { msg: result, metadata: metadata, msgType: msgType };
```

### 6.4 与旧网关映射对齐

- **键源一致**：脚本的 `FACTOR_MAP` code 必须与旧 `sl-gateway` 的 `seed-mapping.sql` / 要素映射页**逐一核对齐**，保证"同一污染因子同一个 code"。
- **键名规划**：脚本 key 用 HJ212 污染因子编码（`W21003`…）时，下游看板/告警引用不变；若要保留词义建议可再加 `metadata` 里的 `factorName`。

### 6.5 验证

- 发一帧：`7e7e...4612...` → 设备最新遥测应出现键 `W21003`（value 对应）而不是 `4612`。
- 控制台/波形验证：`msgType=POST_TELEMETRY_REQUEST`、Transform 命中映射、Save Timeseries 成功。
- 原始要素：`rawFrame` client 属性应存有该帧 hex，可交叉核对。

## 8. 已知冲突与注意事项

1. **端口冲突（最直接）**：内嵌单体与独立微服务都默认监听 8501，同主机需二选一或改 `bind_port`。
2. **in-memory 单节点 ACCESS_TOKEN 认证偶发超时**：属 TB dev 单节点 transport-api 稳定性问题（MQTT basic 路径通常不受影响），换进程或 Kafka 后稳定，**非 SL651 代码缺陷**。
3. **缺失 `configuration` 导致编辑不能保存**：REST 直建 profile 漏传 `configuration` 时前端 `Validators.required` 不通过，保存置灰；UI 正常新建会补 `{type:DEFAULT}`。建议后端对空 `configuration` 做默认化兜底（可选待办）。
4. **状态报 vs 遥测分流**：`isStatusReport` 仅按功能码 `0x35` 判定；厂商若用其它功能码表达事件上报，需在 `isStatusReport` 扩展。
5. **入库位置**：`statusReportAsAttribute=true` 时状态/事件报进属性；如需全部进最新遥测置 `false`。
6. **RPC 应答启发式匹配**：SL651 应答帧不带 TB requestId，靠"命令→应答功能码集"匹配且同一时刻仅最新一条 RPC 生效，需按终端厂商校准 `Sl651RpcMethod`。
7. **Docker 镜像构建未接线**：`docker-compose.yml` 已就位，但 `tb-sl651-transport` 镜像 Dockerfile/构建接线未补齐，`docker compose up` 前需补齐。
8. **规避核心重复改动**：改枚举/`@JsonSubTypes`/前端 switch 分支时，保持 core diff 最小，升级需同步重打这些点。
